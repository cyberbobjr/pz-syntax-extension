# CLAUDE.md

VS Code extension "Project Zomboid Script Support" (Marketplace publisher `cyberbobjr`): language support for Project Zomboid script files (`media/scripts/*.txt`), currently for **Build 42.21**.

## Commands

```sh
npm install
npm run compile            # tsc → out/
npm test                   # compile + node:test on out/test/*.test.js
npm run coverage
npm run test:integration   # launches a real VS Code (downloads it into .vscode-test/) on test-fixtures/workspace
npm run generate-schema    # rebuilds data/schema.json from the installed game (see below)
npx vsce package           # builds the .vsix (runs compile through vscode:prepublish)
```

Some tests check every vanilla script of the installed game: no diagnostics, and formatting does not change what the game reads. They are skipped when the game is not found. The game is found through Steam; set `PZ_SCRIPTS` to point to a `media/scripts` folder instead.

## Architecture

```
src/parser/        scriptParser.ts (block tree with offsets), recipeLine.ts (craftRecipe input/output lines)
src/schema/        schemaKey.ts (block → schema key), schema.ts (data/schema.json access), descriptions.ts (hand-written docs)
src/analysis/      pure features: diagnostics, completion, hover, references, scriptIndex, formatter, symbols, context, similarity
src/game/          gameLocator.ts: finds the game through Steam, including libraryfolders.vdf libraries
src/vscode/        thin VS Code glue: providers, index service, document cache
src/extension.ts   activation and registration
src/test/          unit tests (node:test); src/integration/: end-to-end test in VS Code
tools/             generate-schema.js + jar.js (zip and class constant-pool reader), plain Node
data/schema.json   generated, committed, shipped in the .vsix
syntaxes/          TextMate grammar (tested with vscode-textmate in src/test/grammar.test.ts)
```

Rules:
- **Nothing under `src/parser`, `src/schema`, `src/analysis` or `src/game` imports `vscode`.** Features are pure functions on `(text, ParseResult, offset, ScriptSchema)` that return spans (offsets). `src/vscode/` converts spans to ranges. Keep it that way so everything stays unit-testable.
- `tools/generate-schema.js` requires the compiled `out/`: compile before running it (the npm script does).

## How the game reads scripts

The parser mirrors `zombie.scripting.ScriptParser`. These facts drive the diagnostics; each was verified against the game jar, the vanilla scripts or real mods:

- **Comments are `/* */` only, and they nest.** `//` is not a comment: the game reads that text as script, so it is reported as an error. `//` only counts at a line start or after `,` `{` `}`, not inside values like `media//x`.
- A block header is the text since the previous `{`, `}` or `,`. Values end at `,` or `}`. A missing comma merges lines: the parser splits them back and reports `missing-comma`, including before a nested block header.
- A block's name sits **before** its `{`, so `blockAt(offset)` on a header returns the parent block. Look for the header among the parent's children.
- Property names are **case-insensitive** (`propertyId()`, which also maps `template!` to `template`).
- `:` is a key/value separator only in `fixing` and legacy `recipe` blocks. Elsewhere `mode:keep` or `Woodwork:2` are values.
- Numbers follow Java `Float.parseFloat`: `0.25f`, `1e2` and `+.5` are valid.
- Build 42 (around 42.13) replaced `Type = X` with `ItemType = base:x`. `Type` appears in no item-related class of 42.21.
- Tags, item types, body locations and weapon categories are namespaced (`base:hammer`). Values in another namespace (`mymod:x`) come from mod registries and are never reported.
- Vehicle parts: only `table install { }` is read. A bare `install { }` is ignored by the game.

## Schema (`data/schema.json`)

Generated by `tools/generate-schema.js` from two sources:
- the vanilla scripts: block structure, property names with their most frequent casing, values and counts;
- string literals of the game classes that parse (`zombie/scripting/...`) or generate (`generation/builders/...`) each block kind, mapped in `CLASS_MAP`.

Key concepts:
- **Schema key** (`schemaKey.ts`):
  - top-level blocks use their type (`item`);
  - nested blocks use `parent/type` (`craftrecipe/inputs`);
  - components use `component:<type>` wherever they appear;
  - xui children are free-form (`xuiskin/*`);
  - `template` is an alias of `vehicle`.
- **strict**: every property vanilla uses was found in the mapped classes, so the mapping is complete and unknown properties can be reported. Non-strict blocks are never checked. The generator prints which blocks are not strict and why.
- **extraKeys** are plausible keys the game reads but vanilla does not use: they are suggested in completion. **acceptedKeys** are *all* identifiers of the classes: validation accepts them, completion never shows them (they contain default values and messages).
- **Registries** (`VALUE_REGISTRIES`): the valid values of some properties, merged with every value vanilla uses. `open: true` (display categories, recipe categories) means mods add their own values: suggest them, never report them.
- `repeatable` properties (e.g. `row`) are exempt from duplicate warnings.
- The game version comes from `~/Zomboid/console.txt` (`version=42.21.0 <hash> demo=`), or from `--version`.

## Updating for a new game build

1. `npm run generate-schema` and read its report: new classes may have to be added to `CLASS_MAP`, and a block that becomes non-strict loses its checks.
2. `npm test`: the vanilla corpus must still produce **zero** diagnostics.
3. Check real mods for false positives. Workshop mods live in `D:\SteamLibrary\steamapps\workshop\content\108600`; look at `*/42*/media/scripts/`, aggregate diagnostics by code and inspect the most frequent ones. Several false-positive classes were only found this way: nested comments, `0.25f`, mod categories.
4. Before claiming the game ignores a key, search the whole jar for it (`tools/jar.js`: `Jar` + `classStringLiterals`).
5. `npm run test:integration`, then update `CHANGELOG.md` and the version in `package.json`.

## Gotchas

- Running the integration test from a terminal inside VS Code: the inherited `ELECTRON_RUN_AS_NODE` / `VSCODE_*` variables make the test instance start as plain Node. `runTest.ts` clears them; keep that.
- `.vscodeignore` must keep `src/`, `tools/`, tests, fixtures and `node_modules` out of the .vsix. `data/schema.json` must stay in.
- The language has no `lineComment` in `language-configuration.json` on purpose: Ctrl+/ must insert `/* */`, never `//`.
- Quick fixes are applied to users' scripts: every fix needs a test that applies it (`applyFix` in `src/test/helpers.ts`).
- The user-facing README is the Marketplace page (English). Commit messages follow conventional commits (`feat:`, `fix:`…).
